## Paso 2 — Carga real por el SDK de Pi

```bash
node tests/acceptance/load-extensions.ts /home/gx10a/Documents/ai/kmp
```

### Primer intento: FAIL, con arreglo de código

Salida inicial:

```
Underpass catalog failed for kmp: Underpass host not connected yet
Underpass catalog failed for made: Underpass host not connected yet
{
  "tools": 8, "active": 4,
  "checks": { "kmpRegistered": false, "madeRegistered": false, "kmpActive": false, "madeControlHidden": true }
}
EXIT=1
```

**Diagnóstico.** `pi` carga `host.ts`, `kmp.ts` y `made.ts` (las tres
extensiones declaradas en `package.json#pi.extensions`) cada una por
separado a través de `jiti`, y `pi-coding-agent`
(`dist/core/extensions/loader.js:411`) crea un `jiti` **nuevo por fichero de
extensión** con `moduleCache: false`. Es decir: cada extensión ve su propio
realm de módulos, aislado de los demás. `ExtensionComposition` guardaba el
`HostExtension` compartido en un campo estático de clase
(`static #host`), asumiendo que las tres extensiones importarían la misma
instancia de `ExtensionComposition.ts` — pero con `moduleCache: false` cada
una evalúa su propia copia de ese módulo, así que cada extensión obtenía su
**propia** instancia de `HostExtension`, nunca conectada (sólo la copia
usada por `host.ts` registra el handler `session_start` que abre la
conexión). Confirmado insertando trazas temporales: `HostExtension` en
`host.ts` tenía un id de instancia distinto al que veían `kmp.ts` y
`made.ts`; por eso `gateway()` en las copias de `kmp`/`made` siempre lanzaba
"Underpass host not connected yet", aunque el host real sí arrancaba y su
socket sí quedaba disponible (verificado por separado con
`node bin/underpass-host.ts <proyecto>` y observando `host.lock`/`host.sock`
aparecer en menos de 2 s).

Este bug es real también en el uso interactivo normal (no sólo en el script
de aceptación): las tres extensiones se cargan igual en `pi` real, vía
`package.json#pi.extensions`.

**Arreglo (TDD).** Se sustituyó el campo estático de clase por un registro en
`globalThis` (mismo objeto de proceso en los tres realms de `jiti`, aunque
las clases sean instancias de módulo distintas):

- Nuevo `src/composition/SharedInstance.ts`: `SharedInstance.get(key, factory)`
  guarda instancias en un `Map` colgado de
  `globalThis[Symbol.for("underpass-pi.shared-instances")]`.
- `src/composition/ExtensionComposition.ts`: `#shared()` ahora usa
  `SharedInstance.get("underpass-pi.host-extension", ...)` en vez de
  `static #host`.
- Test nuevo `tests/unit/composition/SharedInstance.test.ts`: importa
  `SharedInstance.ts` dos veces con cache-busting (`?realm=a`, `?realm=b`)
  para forzar dos evaluaciones de módulo distintas — reproduciendo el
  aislamiento real de `jiti` — y comprueba que el registro sigue
  compartiendo la instancia entre ambas.

`npm test` — exit 0 (gates de cobertura 80 % líneas/ramas/funciones sobre
`src/**`, con exclusión de `src/adapters/inbound/pi/entry/**`, sin
regresiones).

Commit: `fix(pi): share HostExtension across extension files via globalThis`
(`4036df9`).
