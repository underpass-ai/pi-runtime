# Aceptación L1 — aprendizaje continuo de tools en la instalación real (Task 12)

Fecha: 2026-09-29. Máquina real del usuario, sin contenedores ni mocks del
producto: sesiones reales de Pi por el SDK, host real del proyecto y los
binarios fijados de `kmp-mcp` y `made-mcp`. El modelo es el proveedor `faux` de
pi-ai (respuestas guionizadas, sin red), como en E1 y O1.

## Cómo se montó

**Decisión de Tirso que sustituye al brief:** la aceptación **no** usa el log de
eventos real de kmp. Se hizo en un proyecto git desechable creado para ella
(`git init` con un README y un commit), con todo el estado aislado en
directorios temporales cortos (el scratchpad de la sesión es demasiado largo
para el socket Unix del host):

| Variable | Qué aísla |
|---|---|
| `XDG_STATE_HOME=<tmp>/l1s` | log de eventos, socket, spool, `telemetry.key`, huellas de catálogo del proyecto y el store de ceremonias de MADE |
| `MADE_SETUP_CONFIG_ROOT=<tmp>/l1cfg` | configuración privada de MADE (0600) para ese store |
| `KMP_MCP_DATA_DIR=<tmp>/l1kmp` | memoria de KMP: un store vacío, nunca el del usuario |
| `L1_ABOUT=project:l1-acceptance` | el `about` que usa el modelo faux en sus llamadas |

Con eso no se escribió nada en el log de kmp, en el store de KMP del usuario,
en `~/.config/underpass-made` ni en `~/.pi/agent/settings.json`, y en el
directorio de estado real no apareció el id del proyecto desechable. Por eso
**no hizo falta copiar ni restaurar ningún log** (pasos 2 y 8 del brief) ni
pedir el permiso que el brief pedía para restaurarlo.

Pi carga el paquete `pi-runtime` desde el checkout principal
`~/Documents/ai/pi-runtime` (registrado en `settings.json`, que no se tocó; no
se ejecutó `underpass update`):

1. `pkill -f 'underpass-host[.]ts'`; ninguna sesión de Pi abierta.
2. `git -C ~/Documents/ai/pi-runtime checkout --detach e984063` (HEAD de
   `feat/l1-learning` con los scripts de aceptación; el producto es el de
   `33aa552`). El checkout principal estaba limpio en `feat/e1-event-log`
   (`010f68a`).
3. Todo (CLI `node ~/Documents/ai/pi-runtime/bin/underpass.ts …` y scripts)
   se ejecutó desde ese checkout.
4. Al terminar: hosts parados y
   `git -C ~/Documents/ai/pi-runtime checkout feat/e1-event-log` (vuelve a
   `010f68a`, árbol limpio). El proyecto desechable y el estado temporal se
   borraron.

### Preparar MADE en el estado temporal

Un `XDG_STATE_HOME` nuevo deja a MADE sin store, sin configuración privada y
sin política de autorización, y `doctor` falla (`made exited (2)`: primero no
existe el directorio del store; después `embedded authorization policy is not
available`). `underpass setup` lo resolvería, pero también reinstala el paquete
en Pi. El script nuevo `tests/acceptance/made-config.ts` hace sólo la parte de
MADE de `setup` con los casos de uso del producto
(`EnsureMadeConfiguration` y `BootstrapMadeAuthorization` con el binario
fijado) contra las rutas que resuelve el entorno, y sólo imprime estados:

```text
made config created
authorization bootstrap OK
```
