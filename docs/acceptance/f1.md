# Aceptación F1 — diagnóstico de argumentos de tools

Fecha: 2026-09-29. Máquina real del usuario: Pi 0.87.1, Node v22.23.2,
`made-mcp` 0.8.0 y `kmp-mcp` 0.24.0 fijados en `~/.local/share/pi-runtime/bin`.
El modelo es el proveedor `faux` de pi-ai (respuestas guionizadas, sin red),
como en S3a.

## El fallo

Pi valida los argumentos de cada tool contra su `parameters` (el inputSchema MCP
compilado por TypeBox). Con esquemas grandes con `oneOf` y
`additionalProperties: false`, como el de `made_design_ceremony`, el error
recorre todas las ramas y no dice qué falla. Con el `repeat` de una etapa grupo
escrito plano (`{max_iterations, step, output_field, equals}` en vez de
`{max_iterations, until: {step, output_field, equals}}`):

```text
Validation failed for tool "made_design_ceremony":
  - stages.0.owner_role_id: must have required properties owner_role_id, instructions
  - stages.0.group: schema is false
  - stages.0: must not have additional properties
  - stages.0.group.repeat.until: must have required properties until
  - stages.0.group.repeat.step: schema is false
  - stages.0.group.repeat.output_field: schema is false
  - stages.0.group.repeat.equals: schema is false
  - stages.0.group.repeat: must not have additional properties
```

## Con F1

`PiToolFactory` da a cada tool un `prepareArguments`, que Pi ejecuta antes de
validar y cuyo error llega al modelo como resultado de la tool. El mismo caso:

```text
made_design_ceremony: the arguments do not match its input schema. Fix these and call it again:
  - stages[0].group.repeat: unknown fields "step", "output_field", "equals"; allowed: max_iterations, until; missing required field "until" — Optional bounded repeat-until policy for the whole group state. — expected {max_iterations, until: {equals, output_field, step}}
```

## Sesión real de Pi

`tests/acceptance/argument-diagnostics-session.ts`: sesión por el SDK con las
extensiones de este checkout, host real de un proyecto git desechable y
`made-mcp` real, con `XDG_STATE_HOME`, `MADE_MCP_STORE_PATH`,
`MADE_SETUP_CONFIG_ROOT` y `KMP_MCP_DATA_DIR` en un temporal sembrado con
`made-config.ts` (el store y la configuración reales de MADE no se tocan). En
fase `design`, el modelo faux llama a `made_design_ceremony` con el `repeat`
plano y después corregido:

```json
"checks": { "flatRefused": true, "flatFocused": true, "noCascade": true, "fixedDesigned": true, "noExtensionErrors": true }
```

El resultado de error que vio el modelo es el mensaje de arriba y la llamada no
llegó a MADE; la corregida devolvió el análisis del borrador (`error_count: 0`).
Con el `PiToolFactory` de `main` en el mismo checkout, el mismo guion da la
cascada de TypeBox (`flatFocused` y `noCascade` en false).

## Prueba diferencial contra el validador de Pi

`tests/acceptance/argument-diagnostics-differential.ts` genera argumentos de cada
inputSchema, los muta (coacciones, nulls, claves que faltan o sobran) y los pasa
por `validateToolArguments` de pi-ai y por `prepareArguments`. La invariante: si
Pi acepta, F1 no rechaza. Con los catálogos vivos (104 tools de MADE y 16 de
KMP), 300 casos por tool y las semillas 1 a 5:

| | por semilla |
|---|---|
| Pi acepta | ~21 600 |
| Pi rechaza | ~14 300 |
| — F1 lo diagnostica | ~9 200 |
| — F1 lo deja a Pi | ~5 100 |
| **Pi acepta y F1 rechaza** | **0** |

Lo que F1 deja a Pi es, sobre todo, lo que no evalúa (`pattern`, `format`,
`uniqueItems`) y los nulls que Pi convierte en `""` o `0` antes de comprobar
`minLength`/`minimum`; ahí el mensaje de Pi ya es corto.
